# Release Assistant 产品与实现规范

状态：首版实现依据。本文记录用户已确认的产品行为；实现、测试和接入工作必须遵循。

## 1. 产品与交付

- 独立仓库 `hwameistor/release-assistant`，提供 TypeScript CLI 和 GitHub Action。
- 核心产物是可审阅的 Release PR，更新版本日志、总 Changelog 和配置声明的 Chart 版本。
- 两个业务仓库通过配置复用工具。接入增加 Release PR 生成、校验和 GitHub Release 正文读取；合并后按原发布触发条件执行，正文采用本次提交中已审核的版本日志。
- 工具不自动合并 PR，不创建或覆盖发布 tag，不构建或发布镜像。
- 已评审日志接入 GitHub Release 正文。预发布属性和已有资产重跑保护仍是后续独立改造，生成流程不依赖这些能力。

## 2. 输入和版本

- 必填：目标仓库、目标分支、发布版本。起始 tag 支持自动发现和手动填写。
- `from_tag` 留空时，由 `from_tag_choice` 选择 `latest`（默认）、`second-latest` 或 `third-latest`。自动候选是截止提交可达历史中、低于待发布版本的最近 3 个 SemVer tag，按 SemVer 从高到低排序，包含预发布版本；支持轻量与附注 tag，允许 `v` 前缀，不按创建时间排序。
- GitHub 原生表单不能动态加载真实 tag 名称，因此使用固定序号选项；解析后的实际候选、选中 tag 和 SHA 展示在运行摘要、PR 的生成详情和快照产物中。候选不足时选择不存在的序号明确失败，不静默回退。
- 手动填写 `from_tag` 优先于自动序号，允许指定候选外或非 SemVer tag，仍需通过祖先关系检查。Action 和 CLI 同时支持两个输入；Action 和示例 prepare job 输出实际 `from-tag`、`from-sha`、`recent-tags`。
- 截止位置支持 tag、分支和提交 SHA；省略时使用目标分支。
- 接受合法 SemVer，允许 `v` 前缀；例如 `v1.1.2-alpha1`、`v1.1.2-rc1`。
- 起始 tag 对应的已有改动不包含在范围中；截止提交的改动包含。
- 必须验证起始提交是截止提交的祖先，截止提交属于目标分支历史。
- 草稿生成可以回顾已有版本；发布 PR 模式发现目标 tag 已存在必须停止。
- 仓库版本、依赖组件版本、JuiceFS 等工具镜像版本分别管理。只修改配置明确声明的版本字段。
- 可选高级输入 `changelog_policy` 对应 Action 的 `changelog-policy` 和 CLI 的 `--changelog-policy`。按用户选择保留一个工作流，字段放在原生运行表单底部；GitHub 原生表单不支持折叠或条件隐藏输入，不模拟不可用的折叠功能。
- 后续发布集成必须识别预发布，不能将 alpha/beta/rc 标记为最新稳定版。

## 3. Git 范围和事实来源

- 由 Git 确定 `from..to` 的提交集合及最终净 diff，不按 PR 合并日期猜测范围。
- 收集范围内提交关联的已合并 PR、原始回移 PR 的来源、正文和最终文件改动。
- 同一 PR 的多个提交去重。回移来源只作为背景，不引入原 PR 中尚未进入目标分支的改动。
- 直接提交、squash、merge、cherry-pick、revert 都必须有可追溯记录。
- AI 依据最终代码改动总结问题、行为变化、用户影响及升级要求，不能直接复制 PR 标题或正文。
- 每个输入变更单元必须被输出条目引用，或者被明确排除并给出原因。机器校验来源和覆盖，不声称能证明语义正确。
- 大量/大体积改动必须分批处理或明确拒绝；不能静默截断后声称完整总结。
- PR 正文、提交消息和 diff 都是待分析资料，不能作为工具权限、凭据或执行指令。

## 4. Changelog 规范

- 使用独立、可版本化的 `changelog-policy.md` 和文本模板。
- 规范来源优先级为运行时 `changelog-policy`、仓库配置的 `policy`、工具内置规范；留空不覆盖下一级。支持相对文件路径、公开 GitHub 文件链接和可直接读取的 HTTPS 文本地址，版式模板仍独立配置。
- 外部规范在每次执行和 Re-run 时重新读取，不改变源码区间快照。GitHub 文件链接先解析为具体提交再读取；提交 SHA 链接固定规范版本。外部请求不携带仓库或模型凭据；无法读取、HTML 页面、非法文本及超过 128 KiB 时明确失败，不回退到另一份规范。
- 运行产物保存实际规范全文、来源地址、GitHub 提交 SHA（如适用）及内容哈希，运行摘要和 PR 展示来源信息。提交到 Release PR 的 manifest 保留原有 schema 和 policyHash，兼容维护分支上已安装的校验器。
- 默认版式为版本标题、Release Changes（分类变更）、分隔线、Upgrade Actions（升级操作）、完整差异链接。升级操作为空时不显示其标题或分隔线；变更分类使用下一级标题，旧模板占位符继续兼容。草稿不把生成日期标作发布日期，生成时间保留在 manifest。
- 每条通常用一句客观陈述，impact 默认留空，仅补充理解该项变化所必需的简短条件。部署步骤和等价配置路径不混入版本条目。参数按需保留并使用行内代码；纯 CI、测试、重构等内部变更写入 excluded 及原因，仍受来源覆盖校验。
- 根目录总 Changelog 和独立版本日志使用同一份渲染结果，历史版本保留不动。
- 默认分类：Breaking Changes、Features、Fixes、Changes、Documentation、Maintenance。
- 每条日志描述实际行为及用户影响；有明确依据才写升级要求、性能收益和兼容性结论。
- 分类正文必须独立、客观说明本版本新增、修改、修复和移除的内容。默认值或版本有变化时写明前后值；新增配置写明公开字段及作用；Fixes 写明触发场景、原有错误及修复结果。问题背景用于解释具体改动，不用“更可靠”“可采用某方案”等主观收益替代修改事实。
- 升级说明仅补充用户需要执行的操作，不能成为版本变化、新增参数或破坏性行为的唯一说明位置。隐藏升级说明后，正文仍必须让用户看清本版本修改了什么。简洁不能靠把正文内容搬进升级说明实现。
- 升级操作以加粗的受影响用户或场景开头，再说明需要执行的操作；跨条目合并相同场景的相关步骤，不重复讲述版本变化。普通运维提醒和未变化的一般性限制留在调研资料或文档中；本次升级引入或暴露的重要兼容性和数据风险必须保留可见提醒。
- 英文每项变化以 15–25 词为目标，summary 与 impact 合计最多 30 词；每条升级操作以 10–20 词为目标，包含场景标签最多 30 词。中文及其他中日韩文字最多 60 个计数单位：每个中日韩字符计一，其余按空白分词各计一。统计可见文字、代码标识符和链接文本，不统计纯标点、格式符、链接地址、渲染器追加的来源链接和复核标记。外部规范也受上限约束，可要求更短。
- 生成后确定性检查长度，超限时两个模型后端均可在原超时预算内改写一次；Copilot 在已有调查会话内继续。再次超限则报告条目和计数，停止生成，不截断或发布不合格正文。必要版本值、配置、前提和风险不能因压缩而省略；长度校验不证明语义完整。已有 manifest 的校验规则保持兼容。
- 小版本有两个用户可见主题时，英文正文与升级操作合计参考 100–180 词、约 3–4 条升级操作；总长度按规模调整，单条上限强制执行，不为达标省略必要风险。
- 多个 PR 解决同一问题时合并；一个 PR 中独立的用户可见改动可以分条，同一组件的所有变化不必挤在一个条目。保留真实兼容性和数据风险；没有取得测试证据不等于项目未测试，不能写成产品缺陷。
- 问题与收益必须有事实依据。仅看到下游组件的配置或版本变化时，只描述可证实的配置能力；关联 issue 的症状不能代替下游修复证据。破坏性行为必须进入 Breaking Changes，不能仅放在升级提醒中。
- 保留 PR/提交链接。弱证据条目要求人工确认。
- 模型返回结构化 JSON，经 schema、引用、覆盖校验后统一渲染 Markdown。
- 规范与模板可以调整，不硬编码现有仓库的历史行文格式。

## 5. Re-run jobs：用户确认的简化流程

- 正常重新生成入口是 GitHub Actions 的 **Re-run all jobs**，不另建多种再生成模式。
- 以“仓库 + 目标分支 + 发布版本”确定唯一生成分支和 Release PR。
- 有未关闭、未合并的对应 PR 就更新；没有才创建；禁止重复创建。
- 每次重跑重新调用 AI，生成文件以最新结果为准，允许覆盖生成文件中的人工编辑。
- 不改写 Git 历史；每次更新形成新提交，可比较和恢复旧版本。
- 已合并或已关闭的 Release PR 必须停止，不自动重新打开或另建同版本 PR。
- 同一版本执行串行化，并在更新远端分支时检查并发变更。
- GitHub 重跑保持原输入及工作流来源。工具每次从配置分支读取最新政策和模板，并记录对应 SHA。
- 每次新运行在调用 AI 前持久化范围快照，记录工作流仓库和 run ID。模型失败后 Re-run 仍使用该运行的原范围；原快照缺失或已被其他运行替换时停止，旧运行不得采用或覆盖新运行的范围。
- 自动模式同时冻结选择序号、候选列表及选中 tag/SHA；同一次运行的 Re-run 不重新发现 tag，不受 tag 新增、移动或删除影响。新建 Run workflow 会重新解析输入并复用 PR，包括旧工具留下的快照；已安装旧版校验器仍可读取快照的既有字段。
- 同一次运行的 Re-run 不推进统计截止 SHA；改模板不能隐式带入新提交。
- 新建 Run workflow 即使 from/to 输入相同也重新确定范围；to-ref 留空使用目标分支最新 HEAD，显式 ref 仍按用户指定解析。仍更新同一个未合并 PR；目标版本或分支改变则属于另一发布。本地 CLI 保持原规则，显式更换截止 SHA 才刷新相同输入的快照。
- 发布目标分支比快照前进时，校验应报过期，要求新建 Run workflow 更新范围，不偷偷扩大原运行范围；生成过程中目标分支发生变化仍拒绝发布。
- 发布 PR 模式在专用生成分支保存快照；dry-run 保存本地状态，预览工作流使用独立缓存保存范围，运行产物用于查看结果。

## 6. 模型与执行位置

- 默认支持 Copilot，以独立的 `COPILOT_GITHUB_TOKEN` 认证；模型名称可配置。
- Prepare release 和 Preview release notes 提供五项模型下拉选择，依次为 `gpt-6.1-sol`（默认）、`gpt-6-astra`、`gemini-4-argon`、`gpt-5.3-codex`、`gemini-3.8-flash`。实际可用性取决于 provider 和账号；展示顺序不代表自动降级顺序。
- 优先级为工作流 `model` / CLI `--model` 高于配置 `ai.model`。模型名原样传给当前 provider，记录到 manifest 和 PR；工具不限制为下拉列表中的五项。
- Re-run all jobs 保留原先选择的模型；更换模型需使用相同发布输入发起新执行，复用同一未合并 PR 并重新解析范围。
- 支持 OpenAI-compatible Chat Completions 端点，以独立 API key 认证；不借用发布凭据。
- 支持 GitHub 托管 runner、自有 runner 和本地 CLI。自有机器调用云端模型不要求 GPU。
- 固定工具依赖版本，不依赖宿主机随机安装的 Copilot 版本。
- 模型步骤不能执行 shell、修改仓库或发布内容；写 GitHub 由确定性程序执行。
- Copilot 必须具备主动调查能力：自行调用只读 GitHub 工具获取 Issue、PR、讨论及代码，根据已读内容选择后续查询，不能只分析程序预先收集的文本。程序固定发布范围、限制访问权限和预算，不替模型预先决定结论。
- 必须实际读取范围内 PR 和正文/来源资料中明确链接的 Issue；未调用工具或缺少必读资料时不能生成成功的发布 PR。对补充资料读取失败，不得编造结果，应限定结论并标记人工复核。
- 范围内 PR 必须成功读取。辅助引用经模型实际请求后明确返回 HTTP 404/410 时，记录为不可获取，不能当作已读证据或引用来源；不能仅因同编号的其他仓库资料可访问就假定两者等价。工具在相关来源的调查结论中保留缺失引用及状态并标记人工复核，最终日志条目继承复核标记，内部改动仍可说明原因后排除。权限、限流、服务端错误、仓库可见性查询失败以及未尝试读取不能按此规则豁免。引用应使用完整 URL 或 owner/repository#number，避免跨仓库裸编号的歧义。
- 查询允许源仓库以及明确关联的公开跨仓库 Issue/PR，最多跟进配置的引用深度。文件读取仅允许发布区间的固定 SHA 以及已查询 PR 的 base/head/merge SHA。外部资料不增加本次发布的来源 ID。
- 默认查询预算为 80 次工具调用、512000 字节返回内容、2 层引用；通过 research.maxCalls/maxBytes/maxDepth 调整。分页及长内容续读位置明确返回，超预算停止本次生成，不以不完整调查伪装成功。
- 每次运行保存 research.json，记录实际工具参数、返回证据、来源、时间、提交及内容哈希；失败也保留记录。重跑重新调查当前 Issue/讨论，但保持发布源码快照不变。记录的是外部证据，不收集模型的私有思考过程。
- Copilot 先主动调查并返回简短、可复核的结论（用户问题/任务、实际实现、结果、证据 URL、局限），再在同一会话中编写发布日志，必要时继续查询。结论必须覆盖发布来源，只能引用工具实际返回的证据 URL。它不是思考过程记录；最终日志应保留已确认的问题背景，不能退化为参数清单。
- Copilot 模型 token、只读查询 token 和发布 PR token 分离。Action 查询默认使用 github.token；CLI 使用 RELEASE_ASSISTANT_READ_TOKEN，无该变量时只访问公开 API，受匿名速率限制。兼容模型端点暂时保留材料分析模式，不宣称已有主动工具调用能力。
- 超时、API 错误、输出不合法、缺少引用时停止，不使用旧结果伪装本次成功，不自动切换付费后端。

## 7. GitHub 集成

- 新增 Prepare release 工作流；支持用户指定版本、分支、from-tag、to-ref。
- 成功创建或更新 Release PR 后，运行摘要首部展示可点击的 PR 链接；Action 和示例工作流的 prepare job 通过 `pull-request-url` 输出同一地址。预览模式不得显示已创建 PR。
- PR 描述直接展示独立版本 Changelog 的完整渲染内容，不再调用模型摘要；生成来源和重跑说明折叠在正文之后。重跑同步覆盖 PR 描述和生成文件，保留同一 PR 链接。
- Release PR 校验快照是否过期、版本字段及生成文件是否正确。
- 修改 `Chart.yaml` 的 Release PR 合并后继续触发现有构建流程。
- 本次生成的版本日志写入 `changelogs/released/<version>/changelog`。发布阶段从固定提交读取并验证版本、非空内容及 manifest 哈希，复制到 Chart 包内的 `RELEASE_NOTES.md`，由 Chart Releaser 直接作为 GitHub Release 正文，不能再次调用 AI。
- 缺少版本日志或 manifest、版本/哈希不匹配、已有 tag 指向其他提交时，在发布前失败；手工发布也需准备匹配的日志及 manifest，不能仅改 Chart 版本。Chart、镜像及 CLI 产物使用相同 SHA 和版本，Operator 手工输入的 release_tag 必须与 Chart 一致。
- HwameiStor 与 Operator 独立 PR；X.Y 对齐，补丁号可独立维护。
- 所有网络写入必须在显式发布 PR 模式下执行；dry-run 不写 GitHub。

## 8. 首版验收

1. 从指定 tag 到目标分支的固定 SHA，生成 `v1.1.2-alpha1` 草稿。
2. 两个已有 tag 之间可以只生成日志预览。
3. 修改模板后重跑，同一范围、同一 PR、新内容、新提交。
4. 第一次模型失败后目标分支前进，重跑仍使用第一次快照，并报告过期。
5. 回移、squash、直接提交和 revert 不丢失事实来源，不把原 PR 全部改动当作已回移。
6. 非法 JSON、未覆盖来源、虚构引用、超大输入、API 权限错误均明确失败。
7. 已发布版本、已合并/关闭 PR 和并发更新不被覆盖。
8. Copilot 和兼容端点使用相同采集、校验、渲染与发布逻辑。
9. 真实 Copilot 运行须产生可检查的 Issue、PR 和代码查询记录；用关联跨仓库 Issue 的发布范围核对生成的问题描述和修复证据。机器检查工具调用和来源覆盖，人工评估语义质量，不能用工具调用次数证明所有结论正确。
